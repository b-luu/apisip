# apisip design

How apisip v1 behaves and why. The README is the user guide; this is the
reference for contributors.

## User experience

```sh
mkdir my-api && cd my-api                           # one folder per API
apisip init https://api.example.com/openapi.json   # interactive; writes apisip.toml, .env, .env.example, .gitignore, .apisip/
apisip list                                         # streams configured in this folder: enabled, mode, schema source
apisip check                                        # dry run: validates config + creds, 1 request per stream, writes nothing
apisip run [--stream users] [--full-refresh] [--strict]
apisip update [<new-spec-url-or-file>] [--check]    # diffs a new spec version against the config and merges it
```

- **Verbs only.** Every subcommand is a verb. Later modes follow the same rule, for example `push` for reverse mode and `listen` for webhooks.
- **One folder per API.**
  - A folder holds one `apisip.toml`, and every command reads the one in the current directory. `-C <dir>` points at another folder, as in git.
  - Without a config, the error says to run `apisip init`. `init` refuses to overwrite an existing config without `--force`.
  - The README quickstart and the `init` output both state this layout.
- **Interactive `init`.** It prompts with `inquire`. Each prompt has a default and a matching flag, so `--yes` plus flags runs with no prompts for scripts and CI.
  1. **Destination:** the current directory by default, or an `s3://bucket/prefix` URL. S3 triggers prompts for the endpoint URL, region and keys.
  2. **Format:** `jsonl` (default) or `parquet`.
  3. **Auth scheme:** a picker when the spec declares several, preselected when it declares one.
  4. **Credentials for that scheme:**
     - a token for bearer or API key;
     - a username and password for basic;
     - a client id and secret for OAuth2 client credentials.

     Secrets are typed without echo and written to `.env` with mode `0600`. `.env.example` keeps the variable names with empty values, and `.gitignore` gets `.env`.
  5. **Streams:** a multi-select of the detected endpoints, all selected by default.
  6. **Primary key,** asked per stream only when the record schema has no `id`.
  7. **Rate-limit plan,** asked only when the spec documents several tiers.

  At the end, `init` prints a summary with each stream's mode, any rate-limit warning, and the next commands to run.
- **Auth in v1:** bearer, API key (header, query or cookie), HTTP basic, and OAuth2 client credentials. Client credentials fetches a token from the spec's `tokenUrl`, caches it, and refreshes it on expiry or on a 401.
- **Retry and pagination** are in v1. `[source.retry]` sets the number of tries, the backoff cap and the retryable statuses.

### `apisip.toml`

Generated by `init` and editable by hand:

```toml
[source]
spec = "https://api.example.com/openapi.json"
base_url = "https://api.example.com/v1"            # from servers[0]
auth = { type = "bearer", token = "${EXAMPLE_API_TOKEN}" }   # bearer | api_key | basic | oauth2_client_credentials
rate_limit = { max_calls = 100, period = "1m" }     # from the spec or the plan picked at init; optional
retry = { max_tries = 8, max_backoff = "60s", on_status = [429, 500, 502, 503, 504] }

[destination]
url = "file://."                                    # default: this folder; or s3://bucket/prefix
format = "jsonl"                                    # jsonl | parquet
rotate = { max_bytes = "128MiB" }

[[streams]]
name = "users"
path = "/users"
records = "/data"                                    # JSON pointer to the record array
primary_key = "id"
pagination = { type = "page_number", param = "page", size_param = "per_page", size = 100 }
incremental = { cursor = "updated_at", param = "since" }                         # server-side filter
# incremental = { cursor = "updated_at", sort = { param = "sort", value = "-updated_at" } }   # early stop
```

- **Variables:** `${VAR}` is interpolated from `.env` and the process env.
- **S3 credentials:** the standard AWS variables, read by `object_store`'s `from_env`: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, and `AWS_ENDPOINT_URL` for any S3-compatible store.
- **Config format:** TOML, the Rust ecosystem default. It is explicitly typed and has no indentation pitfalls.

### Rate limits

OpenAPI has no standard rate-limit field, so `init` reads what specs actually publish, in this order:
1. **Vendor extensions** such as `x-ratelimit` or `x-rate-limit`, on the root, the paths or the operations.
2. **Declared response headers** (`X-RateLimit-Limit`, `RateLimit-Policy`). They show the API reports its limits at runtime.
3. **Description text** matching a pattern like "N requests per second|minute|hour", with any plan or tier names found next to it.

The results:
- **One limit found:** it is written to `rate_limit`.
- **Several tiers found:** `init` asks which plan the user is on.
- **Nothing found:** `rate_limit` is left unset.
  - `init` prints a warning that no rate limit was found in the spec. The warning shows the exact `rate_limit = { max_calls = …, period = "…" }` line to add, and tells the user to check the provider's docs or pricing page.
  - `check` and `run` repeat a one-line warning while `rate_limit` is unset.

In every case the runtime also adapts to live headers.
- **Budget headers:** with `X-RateLimit-Remaining` / `X-RateLimit-Reset` or `RateLimit` / `RateLimit-Reset`, the throttle waits for the reset before the budget runs out.
- **`Retry-After`** on a 429 always wins.
- **Effect:** a wrong or missing static limit costs a few retries, not a failed run.

### Incremental runs

`run` is incremental by default. Each stream stores a watermark, the highest cursor value seen, and `--full-refresh` ignores it. A stream gets one of three modes, chosen by `init` from the spec and shown by `list`:

1. **Filter.** The spec exposes a server-side filter param (`since`, `updated_after`, `modified_since`…) matched with a record cursor field. The next run sends `param=<watermark>`.
2. **Early stop.** There is no filter param, but the endpoint can sort by the cursor in descending order: a `sort` / `order_by` / `sort_by` param, optionally with `order` / `direction`, whose enum or description allows `updated_at` descending. `run` requests that sort, pages normally, and stops as soon as a page holds only records whose cursor is below the watermark. The records of the last page that are below the watermark are dropped.
   - **Runtime guard:** if the cursor ever increases within a run, the API is not sorted as promised. The stream finishes this run as a full fetch, a warning is logged and recorded in the manifest, and `list` shows `early stop (unreliable)`.
   - When both a filter and a sort exist, filter mode wins.
3. **Full refresh.** Nothing usable exists, so every run re-downloads the stream. Each run's output is a complete snapshot under its own `run_id=` sub-partition.

Delivery is **at least once**. The comparison against the watermark is inclusive (`≥`), because losing a record at the boundary is worse than repeating one.

### Output model: an append-only change log

apisip never updates or deletes rows it has written. Every run appends what it captured. This sets the grain of the output, and the README explains it up front, in a section named "Understanding the output":

- **Filter and early-stop streams:** one row per version of a source record that a run observed. A record created and then updated twice, with a run after each change, appears three times.
  - Changes between two runs are not captured. A record updated five times between runs appears once, in its latest state.
  - The output is a history of snapshots taken at run times, not a full change-data-capture feed. The README states this plainly.
- **Full-refresh streams:** one complete snapshot per run.

Each record carries two metadata fields, in JSONL and in Parquet: `_apisip_run_id` and `_apisip_extracted_at`.

apisip generates the downstream views instead of leaving each user to rebuild them. For each stream, `run` writes two DuckDB SQL files under `_apisip/views/`:

- **`<stream>_current.sql`:** the current state, with one row per primary key: the latest cursor, ties broken by `_apisip_extracted_at`.

  ```sql
  select * exclude (_rn) from (
    select *, row_number() over (partition by id order by updated_at desc, _apisip_extracted_at desc) as _rn
    from read_parquet('users/**/*.parquet')
  ) where _rn = 1
  ```

  For full-refresh streams, it is the latest committed snapshot.
- **`<stream>_history.sql`:** a slowly changing dimension type 2 view.
  - It keeps one row per (key, cursor value), so exact duplicates are collapsed.
  - It adds `valid_from` (the cursor), `valid_to` (the next version's cursor, via `lead()`), and `is_current`.
  - For full-refresh streams, it is derived by comparing consecutive snapshots.

The README explains the grain and shows both views. It also shows how to port the same window-function pattern to any warehouse's SQL, and how to load the views in DuckDB. The SQL uses only standard window functions, so it runs nearly unchanged elsewhere.

### Keeping duplicates in check

Duplicates have three sources: the inclusive boundary, a re-run after a crash, and full-refresh snapshots. The generated views remove them downstream. Upstream, apisip keeps them rare:

1. **Staged commit.** Each stream is written to `_apisip/staging/<run_id>/`. When the stream finishes, the commit runs these steps in order:
   1. move the files into the data path (an atomic rename locally, a server-side copy on S3);
   2. advance the watermark;
   3. write the manifest;
   4. clean up the staging files.

   A failed run leaves no data and no moved watermark. Duplicates from a crash remain possible only between steps 1 and 2.
2. **Ranges and overlaps in the manifest.** The run manifest records per stream the status, the requested range and the cursor range actually observed. An overlap with an earlier committed run is flagged in the manifest and printed by `run`.
3. **Primary key detection.** OpenAPI has no primary-key marker. `init` picks `id` when it is present and asks otherwise, and the value stays editable in `apisip.toml`.

### `update`: follow API changes

`init` stores two files in `.apisip/`: a snapshot of the spec it used, and the config it generated from that spec (the baseline). `update` uses both:

1. It fetches the spec again, from the URL in `apisip.toml` or from a new URL or file passed as an argument.
2. It re-detects from the new spec and diffs the result against the baseline. It reports:
   - added and removed endpoints;
   - changed params, pagination, incremental mode, auth or rate limits;
   - response schema changes: fields added, removed or retyped.
3. It merges three ways, between the old baseline, the new detection and the current `apisip.toml`:
   - A value the user never edited is updated silently.
   - A value both the user and the spec changed is a conflict. `update` shows both values and asks.
   - A removed endpoint is disabled, not deleted, so its data and watermark stay.
   - New endpoints are offered in a multi-select, unselected by default.
   - **Auth is always re-confirmed** through the `init` picker and prompts. The current scheme is preselected, and each credential shows its masked current value (`****abcd`), so Enter keeps it.
     - New and dropped schemes are labelled `new` and `removed`.
     - If the scheme in use was dropped, there is no default, and the user must pick another.
     - `--yes` keeps the current auth, and fails with a clear error if the scheme in use was dropped.
4. It rewrites `apisip.toml` with `toml_edit`, which keeps the user's comments and formatting. Then it refreshes the snapshot and the baseline.

`update --check` prints the diff only, and exits with code 1 when something changed, so a CI job can flag a spec change.

### Schema: the spec is the source of truth

- **Parquet columns come from the endpoint's response schema,** built before the first request. The schema is stable across files and runs, and numbers never decay into strings.
  - `integer` gives Int64, and `number` gives Float64.
  - `boolean` gives Boolean.
  - `string` with `format: date-time` gives Timestamp(µs, UTC), and with `format: date` gives Date32. Other strings, enums included, give Utf8.
  - An object with declared properties gives a Struct, and an `array` gives a List.
  - `oneOf`, `anyOf`, free-form objects and an empty schema give a JSON string.
- **All columns are nullable,** because specs under-declare `nullable` and `required`.
- **Undeclared fields** go into one `_apisip_extra` JSON-string column, so no data is lost.
- **Values that violate the spec** (e.g. `"123"` where `integer` is declared) are never silently cast.
  - The whole record goes to `<stream>/_quarantine/<run_id>.jsonl` with the reason.
  - It is counted in the manifest and reported as drift.
  - `run --strict` fails instead.
- **No response schema at all:** the stream falls back to inference from the first records. Int plus float widens to float, and any other conflict widens to string. `list` shows `schema: inferred`.
- **JSONL** keeps records exactly as received, plus the metadata fields. The drift check still runs, but nothing is quarantined.
- **Drift report:** `run` compares every record with the spec. Undeclared, missing and mistyped fields go into the manifest with counts and one example each. A summary prints at the end of the run, and `update` refers to it.

## Architecture

One crate, a lib plus the `apisip` binary:

- **`spec/`:** loads a URL or file in JSON or YAML, walks `serde_json::Value`, and resolves local `$ref`s. One walker covers OpenAPI 3.0, 3.1 and Swagger 2.0.
- **`detect/`:** turns a spec into stream definitions.
  - **Candidates:** `GET` with no required path params, whose success response declares a JSON body. The rest are listed as "skipped: needs parent stream", since child streams are a follow-up.
  - **Records:** the 200 schema is an array, or an object with one array property.
  - **Pagination:** page_number, offset, cursor, next_url. At runtime, a `Link: rel="next"` header is followed when present.
  - **Incremental mode:** filter, early stop or full refresh, as described above.
  - **Primary key, auth schemes and rate limits.**
  - **Output:** detection is best-effort. It writes plain TOML the user can correct, and `check` reports what fails.
- **`config/`:** serde types, env interpolation, validation, and folder lookup with `-C`.
- **`prompt/`:** the `inquire` flows shared by `init` and `update`, plus the `.env` writer.
- **`auth/`:** bearer, API key, basic, and OAuth2 client credentials with token caching.
- **`http/`:**
  - `Throttle`: a rolling window that also adapts to live headers.
  - `RetryPolicy`: success and retry predicates, with delays from `Retry-After` first, then `2^n + jitter` up to a cap.
  - `Paginator` trait: `next(&resp, &body) -> Option<RequestPatch>`.
  - `EarlyStop` guard.
  - Each stream is an async `Stream<Item = Result<Value>>`. Streams run concurrently, 4 at a time by default.
- **`schema/`:** spec-to-Arrow mapping, record validation (drift and quarantine), and the inference fallback.
- **`sink/`:** an `object_store` destination for `file://` and `s3://`, behind a `Writer` trait.
  - **JSONL layout:** `<stream>/dt=<YYYY-MM-DD>/[run_id=<id>/]<stream>-<run_ts>-<seq>.jsonl`.
    - Local commits merge into the latest part while it is under `max_bytes`: write a temp file, then rename. This is the "append to the same file" behaviour.
    - S3 objects are immutable, so each run or rotation adds a new part.
  - **Parquet:** row groups of about 10k rows, written with `AsyncArrowWriter` to an `object_store` writer. The file rotates at `max_bytes`.
- **`state/`:** the staged commit, the watermarks in `<destination>/_apisip/state.json`, and the run manifests in `_apisip/runs/<run_id>.json`.
- **`views/`:** generation of the current-state and history SQL files.
- **`update/`:** the spec diff, the three-way merge against `.apisip/baseline.toml`, and in-place edits with `toml_edit`.

Main crates: `tokio`, `reqwest` (rustls), `serde`, `serde_json`, `serde_yaml_ng` (reads YAML specs), `toml`, `toml_edit`, `clap`, `inquire`, `dotenvy`, `object_store` (aws), `arrow`, `parquet` (async, object_store), `futures`, `async-stream`, `tracing`, `thiserror`, `anyhow`, `chrono`, `url`, `rand`. Dev crates: `wiremock`, `tempfile`, `assert_cmd`, `rexpect`.

## Repo setup

- **`flake.nix`** is part of the repo and only uses inputs from nixpkgs:
  - `packages.default`, built with `rustPlatform.buildRustPackage` from `Cargo.lock`;
  - `apps.default`, so `nix run github:<owner>/apisip -- init …` works;
  - `devShells.default` with cargo, rustc, clippy, rustfmt, rust-analyzer and duckdb;
  - `checks` running the test suite.

  The README documents `cargo install` first and Nix as an alternative. During development, `nix develop` provides the toolchain locally, so no ad hoc shell is needed.
- **Other files:**
  - `README.md` with the quickstart, "Understanding the output", "Alternatives" and "Works well with";
  - `AGENTS.md`, including the no-private-references rule and the line against citing plan IDs;
  - `LICENSE-MIT` and `LICENSE-APACHE`;
  - `.github/workflows/ci.yml` with fmt, clippy, test and `nix flake check`;
  - `docs/design.md`;
  - `docs/roadmap.md`, holding the follow-ups until they become issues.
- **`examples/mock-api/`:** an axum server with its own spec. It covers:
  - bearer and OAuth2 client credentials;
  - the four pagination styles;
  - a filter-mode stream, an early-stop stream (plus one that lies about its sort) and a full-refresh stream;
  - 429-then-OK, rate-limit headers, one undeclared field and one mistyped value;
  - a v2 spec for `update`.

  The e2e tests run against it, and so does the README quickstart.

## Verification

- **Gates:** `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, `nix flake check`, `nix build`, and `nix run . -- --help`.
- **Unit tests:**
  - detection against the fixture specs (3.0, 3.1 and 2.0, `$ref` chains, wrapped arrays) for pagination, mode, primary key, auth and rate limits, including a spec with several tiers;
  - each paginator, `RetryPolicy` with `Retry-After`, `Throttle` timing and its header adaptation;
  - OAuth2 token fetch, caching and refresh on a 401;
  - the early-stop cut-off, and the guard on an unsorted response;
  - spec-to-Arrow mapping, quarantine and `_apisip_extra`, and widening in the inference fallback;
  - JSONL rotation, and the atomic local merge;
  - the staged commit: a crash injected after staging leaves the data path and the watermark unchanged;
  - overlap flagging;
  - the three-way merge cases.
- **Interactive flows:** `init` and `update` are driven through a pseudo-terminal with `rexpect`. The tests assert:
  - the files written, with `.env` at mode `0600` and listed in `.gitignore`;
  - the auth picker;
  - Enter keeping the current credentials in `update`.

  The flag-only `--yes` path is tested as well.
- **End-to-end through the real binary against the mock API:**
  - `init` → `check` → `run`, in JSONL and in Parquet. DuckDB counts match the server totals, and Parquet column types match the spec.
  - A second run fetches only the new records for the filter and early-stop streams, and adds a snapshot for the full-refresh stream.
  - Mutating records in the mock and re-running produces several versions per key. `_current.sql` returns exactly one row per key with the latest values, and `_history.sql` returns correct `valid_from` / `valid_to` values.
  - A missing token produces a clear error from `check`. A missing rate limit produces the warning with its hint.
  - The undeclared field lands in `_apisip_extra`, and the mistyped record in quarantine. `--strict` fails.
  - `update` from v1 to v2: unedited values change, an edited value prompts, the removed endpoint is disabled, comments survive, and `--check` exits 1 or 0.
- **S3:** any S3-compatible server (the test was run against SeaweedFS), with `run` to `s3://` and a read-back through DuckDB `httpfs`. The test is gated behind `APISIP_TEST_S3=1`.
- **Real specs:**
  - `init --yes` + `run` against the live Petstore v3 server.
  - `init --yes` (detection only) on a large public spec, GitHub's REST spec, as a parser stress test.
